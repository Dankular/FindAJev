# What to test with Cedar

Everything the harness uses Cedar for, plus the wider list of things Cedar can be used to test here.
**Status**: ✅ implemented (runs today) · 🟡 designed, small step from what exists · 🔬 needs a check that I have not done yet (noted where).

Run any implemented check: `findajev cedar-suite [--list] [--checks a,b] [--json]`, from the dashboard's **Cedar checks** tab, or `POST /checks`.
The *gate* checks (`policy-validate`, `golden-cases`, `conformance`) run before every benchmark job and in the Docker build.

## 1. Implemented checks (`cedar-suite`)

| id | gate | what it proves |
|---|:-:|---|
| `policy-validate` | ✅ | every policy validates against `schema.cedarschema` in **strict** mode (attribute typos, type errors, missing `has` guards) |
| `golden-cases` | ✅ | `cases.json`: hand-written expected decisions for our policies, incl. exact reason sets (`"exact": true`) and guardrail boundaries |
| `conformance` | ✅ | `conformance/*.json`: Cedar's own semantics on the linked library (see §2) |
| `properties` | ✅ | invariants over **every** label combination of every pack (§3) + safety-net findings |
| `mutation` | | break each policy (delete / flip effect / swap literal / relax comparison); a mutant no golden case catches is a hole in the tests |
| `gold-coverage` | | every dataset row through Cedar on gold labels: which actions fire, which policies never decide anything |
| `noise-sweep` | | corrupt gold labels at 5–40 % and measure Unsafe / Overblocked rates per pack: fragility to classifier mistakes, no model needed |
| `bench` | | Cedar authorization latency per pack |

Current state: 44 policies, 13 packs, 86 golden cases, 115 conformance cases, Cedar 4.13.0 (language 4.5), mutation score 98/98.
The properties check found 13 real gaps in the first version of the policies (safety `forbid`s with no human path, e.g. `account_closure`
tickets, `mortgage`, `refund_request`); they are fixed and pinned by golden cases.

## 3. Properties checked exhaustively (per pack, over all label combinations × options × confidence grid)

| property | kind |
|---|---|
| **confidence-floor** — below the bar, no autonomous (`AutoAct`) action is ever allowed | hard |
| **guard-non-interference** — at or above the bar the guard changes nothing | hard |
| **monotone-in-confidence** — more confidence never turns an allow into a deny | hard |
| **order-invariance** — reversing policy order changes neither decision nor reasons | hard |
| no-human-path-after-safety-forbid — a `forbid` blocked automation but nothing else is allowed | finding |
| bot-and-human-both-allowed — an autonomous action and `EscalateHuman` both allowed | finding |

## 4. Ideas, grouped

### Engine and upgrade safety
* ✅ Conformance on the linked Cedar version (catches behavioural drift on upgrade).
* 🟡 **Differential upgrade test**: run the same conformance + golden + properties against the previous library build (4.5) and diff every answer.
* 🟡 **Cross-binding parity**: same policies + requests through the Rust `cedar` CLI vs CedarDotNet.
* 🟡 **FFI hygiene**: repeated calls keep RSS flat (`free_string`), and concurrent calls are safe.
* 🟡 Performance regression gate on `bench` (p95 budget per pack).

### Policy quality
* ✅ Mutation testing, gold coverage, dead-policy detection.
* 🟡 **Shadowing / redundancy**: policies whose id never appears in any decision over the exhaustive state space.
* 🟡 **Schema evolution**: add/remove/retype an attribute and list the policies that break (validate under old vs new schema).
* 🔬 **Symbolic analysis** (policy equivalence, implication, "does this forbid make that permit unreachable", policy-set diff): Cedar has analysis tooling, but I have not checked that it is available in the crate features this build uses.
* 🟡 Lint in CI: `format` idempotence over every policy; every policy carries an `@id` (already enforced at load).

### Robustness
* 🟡 **Adversarial context**: 100 kB strings, unicode/homoglyph values, `*` and escapes against `like`, integer extremes, empty sets, deeply nested records.
* 🟡 **Entity graph stress**: hierarchy cycles, depth 1000, wide fan-out; latency vs entity count and policy count.
* 🟡 **Schema-driven request generation**: enumerate every valid request the schema allows and assert no engine errors and deterministic answers.
* 🟡 Explainability: every deny is explained by a `forbid` id or by "no permit matched"; every allow by ≥1 permit id.

### Using Cedar around the classifier (the model is the input, Cedar the oracle)
* ✅ **Guardrail outcomes per test** (Unsafe / Overblocked / WrongButSafe) for Classification, Automation, Retrieval, Tools.
* ✅ **Confidence-aware abstention** (`guard.low-confidence*`, thresholds are runtime parameters; results record which were used).
* ✅ **Label-noise sensitivity** (`noise-sweep`).
* 🟡 **Retrieval with access control as a pre-filter**: Cedar *partial evaluation* turns a user's permissions into a residual filter; test that filter-then-rank equals rank-then-filter and never leaks a restricted passage.
* 🟡 **Tool-call gating with approvals**: sequences (`RequireApproval` → `InvokeTool`) with `context.approved`; separation of duties (requester ≠ approver).
* 🟡 **Time-bound access** with `datetime`/`duration`: business hours, expiry, DST edges.
* 🟡 **Network-bound access** with `ip` ranges from a request-origin label.
* 🟡 **Multi-tenant isolation fuzz**: generated tenants/resources; metamorphic check that renaming tenants never changes decisions and no cross-tenant allow exists.
* 🔬 **Prompt-injection / jailbreak guardrail suite**: classifier labels "injection: yes/no", Cedar forbids tool use. Needs a dataset; I have not verified one — use the `jsonl` loader with your own rows or a dataset you pick.
* 🔬 **Content moderation / PII redaction suite** (toxicity, PII spans → publish/redact/escalate): same — dataset not verified.
* 🟡 **Calibration-aware thresholds**: fit the confidence bar from data instead of the current heuristic (60 / 35).

### Operations
* 🟡 Policy change review: on every policy edit, run mutation + properties and post the diff of Unsafe/Overblocked rates (a "policy regression report").
* 🟡 Audit trail: persist every test's Cedar request + decision + policy ids (already streamed as `verdict` events) for replay.

## 5. Adding your own

* **A dataset/suite**: add an entry to `suites.json`. Use loader `jsonl` for your own rows (`text`, `labels`, `gold`, optional `optAttrs` for per-option facts that become Cedar context). Add a pack in `policies/packs.json` to enforce policies on it.
* **A policy parameter**: put `{{name}}` in a `.cedar` file and the default in `params.json`; runs can override it (`--param name=value`, or the dashboard) and are ranked separately.
* **A Cedar check**: add a `CheckInfo` + a `case` in `src/FindAJev.Bench/CedarChecks.cs`; it appears in `--list`, the API and the dashboard.
* **A conformance case**: add it to `tools/build_conformance.py` and regenerate.
